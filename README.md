# Построение аналитики EdTech-платформы с нуля: архитектура, качество данных и метрики

Портфельный проект: построение аналитической системы с нуля для вымышленной онлайн-школы по подготовке к ЕГЭ.

**Стек:** Python · SQL · DuckDB · Markdown  
**Период данных:** январь 2024 — июнь 2025  
**Статус:** завершён. Дашборд — Проект 2.

## Проблема

Онлайн-школа по подготовке к ЕГЭ росла, но аналитика отставала. Метрики считались по-разному в разных отделах. Данные проверялись вручную или не проверялись вовсе. Выгрузки из разных источников сводились вручную и увеличивали риски ошибок. Знания о том, как всё устроено, жили в голове одного аналитика.

Задача — построить систему, где процессы задокументированы, метрики считаются одинаково, ошибки находятся автоматически, а работа системы не зависит от одного человека.

## Результаты

| Что сделано | Результат |
|---|---|
| Синтетический датасет | 6 таблиц, ~38 000 строк, 9 намеренных аномалий |
| Система проверки качества | 20 автоматических проверок, снижение ошибок на **−99%** |
| Трёхслойная DWH-архитектура | raw → staging → marts в DuckDB |
| Витрины данных | 5 витрин, покрывают все ключевые бизнес-домены |
| Документация | 7 документов — от Data Dictionary до staging_decisions |

## Быстрый старт

### Требования

```bash
pip install pandas numpy duckdb
```

### Запуск

```bash
# 1. Сгенерировать сырые данные
python scripts/generate_data.py

# 2. Проверить качество сырых данных
python scripts/check_quality.py
# → выбрать режим 1 (raw)
# → сохранится reports/quality_raw.md

# 3. Создать базу данных и витрины
python scripts/init_db.py

# 4. Проверить качество после очистки
python scripts/check_quality.py
# → выбрать режим 2 (staging)
# → сохранится reports/quality_staging.md

# 5. Сравнить два отчёта
python scripts/check_quality.py
# → выбрать режим 3 (compare)
```

После запуска `init_db.py` база `data/db/platform.duckdb` содержит три схемы:

```
raw      → 6 таблиц, сырые данные как есть
staging  → 6 таблиц, очищенные данные
marts    → 5 витрин, готовые метрики
```

## Намеренные аномалии в данных

Генератор намеренно создаёт 9 типов аномалий — чтобы показать работу системы контроля качества.

|Код|Аномалия|Кол-во|
|---|---|---|
|A1|Дублирующиеся email|~50|
|A2|Регистрация в будущем|30|
|A3|Курсы с ценой 0|5|
|A4|Enrollment раньше регистрации|100|
|A5|Отрицательные платежи|40|
|A6|Нулевые платежи при success|20|
|A7|Orphan records в payment_attempts|~200|
|A8|Нулевые расходы при показах|15|
|A9|Даты в будущем (ad_costs)|5|

После очистки staging-слоем: **737 → 5 записей с ошибками (−99%)**. Единственная оставшаяся аномалия — A3 (курсы с ценой 0): решение намеренно оставлено продакт-менеджеру, а не автоматике.

## Ограничения проекта

Следующее намеренно не реализовано — описано как целевое состояние в `docs/part2_to_be.md`:
- **Инкрементальная загрузка** — база пересоздаётся полностью. В продакшне: загружать только новые данные за день.
- **Историчность (SCD2)** — нет истории изменений атрибутов. В продакшне: хранить все версии цены курса, статуса студента.
- **Оркестрация** — скрипты запускаются вручную. В продакшне: Airflow или cron по расписанию с алертами.
- **Дашборд и построение форм отчётности** — вынесены в самостоятельный проект.

## Навыки, которые демонстрирует проект

- **Python** — генерация реалистичных данных с контролируемыми аномалиями, скрипты проверки качества с интерактивным меню, автоматическое создание и наполнение DuckDB.
- **SQL** — оконные функции (LAG, SUM OVER), многошаговые CTE, когортный анализ, LEFT JOIN с агрегациями, условные агрегаты.
- **Аналитическое проектирование** — AS-IS/GAP/TO-BE анализ, трёхслойная DWH-архитектура, Data Dictionary с владельцами метрик, система отчётности с получателями и форматами.
- **Data Quality** — 20 автоматических проверок с уровнями критичности, сравнение «до/после» с процентом снижения ошибок, документация каждого решения по очистке.
