# Часть 2. GAP Analysis и TO-BE: целевая архитектура аналитики

## 1. GAP Analysis — что не так с текущей системой

На основе описания AS-IS можно сформулировать четыре класса проблем, каждый из которых создаёт конкретные бизнес-риски.

### 1.1 Нет единого определения метрик

**Проблема.** Выручку, конверсию и активность считают три человека тремя разными способами. Определения нигде не зафиксированы.

**Риск.** Решения принимаются на основе цифр, в корректности которых нельзя быть уверенным. Полчаса совещания уходит на выяснение, почему у аналитика конверсия 4.2%, а у маркетолога — 6.1%.

**Что нужно.** Единый каталог метрик с формулами, фильтрами и ответственными — Data Dictionary.

### 1.2 Данные не проверяются на качество

**Проблема.** Аномалии в данных (отрицательные платежи, записи с некорректными датами, дубли) попадают в расчёты и искажают метрики. Никто систематически это не проверяет.

**Риск.** Выручка занижается из-за отрицательных сумм. Воронка конверсии искажается из-за записей с невозможными датами. Ошибки обнаруживаются случайно и поздно.

**Что нужно.** Автоматическая система проверки качества данных, которая запускается после каждой загрузки и сигнализирует об аномалиях.

**Масштаб проблемы в нашем датасете (до очистки):**

| Аномалия | Записей |
|---|---|
| Дублирующиеся email | 100 |
| Enrollment раньше регистрации | 164 |
| Отрицательные платежи | 40 |
| Нулевые платежи при success | 20 |
| Платёж раньше регистрации | 62 |
| Orphan records в попытках оплаты | 200 |
| Нулевые расходы при показах | 15 |
| **Итого** | **601** |

### 1.3 Нет слоя трансформаций

**Проблема.** Аналитик пишет SQL напрямую к сырым данным. Фильтры («только успешные платежи», «только опубликованные курсы») каждый раз пишутся заново и могут отличаться.

**Риск.** Разные запросы дают разные результаты для одной метрики. Новый аналитик не знает, какие фильтры нужно применять.

**Что нужно.** Слой очищенных данных (staging), поверх которого строятся все витрины. Фильтры применяются один раз, а не в каждом запросе.

### 1.4 Нет интеграции источников данных

**Проблема.** Данные из рекламных кабинетов загружаются вручную раз в неделю. Данные из CRM запрашиваются у менеджера по необходимости. Сводная картина «выручка + расходы на рекламу» собирается руками.

**Риск.** Метрику CAC (стоимость привлечения) посчитать нельзя в режиме реального времени. ROAS — тоже. Маркетинговые решения принимаются без актуальных данных об эффективности каналов.

**Что нужно.** Единое хранилище, куда регулярно поступают данные из всех источников. Аналитик работает с одной системой, а не собирает данные из пяти мест.

### Сводная таблица GAP

| Проблема | Текущее состояние | Целевое состояние | Приоритет |
|---|---|---|---|
| Метрики считаются по-разному | Нет документации | Data Dictionary | 🔴 Высокий |
| Аномалии в данных не выявляются | Ручная проверка | Автоматический DQ-скрипт | 🔴 Высокий |
| Нет слоя трансформаций | SQL к сырым данным | Staging-слой | 🔴 Высокий |
| Нет интеграции источников | Ручные выгрузки | Единое хранилище | 🟡 Средний |
| Зависимость от одного человека | Знания в головах | Документация + git | 🟡 Средний |
| Нет регулярной отчётности | Дашборд обновляется вручную | Автоматизированная отчётность | 🟡 Средний |

## 2. TO-BE — целевая архитектура

### 2.1 Принципы системы

Система построена на четырёх принципах, которые напрямую закрывают боли из AS-IS.

**Единый источник правды.** Каждая метрика считается ровно одним способом, зафиксированным в Data Dictionary. Если нужно узнать выручку — смотришь в `mart_revenue`. Не пишешь SQL заново.

**Прозрачность фильтров.** Все правила очистки данных описаны в `staging_decisions.md` и реализованы в одном месте — `init_db.py`. Новый аналитик понимает систему за день.

**Автоматический контроль качества.** После каждого обновления данных запускается `check_quality.py`. Аномалии видны немедленно, а не через три дня когда кто-то заметит расхождение в отчёте.

**Воспроизводимость.** Вся система пересоздаётся из исходных данных одной командой. Нет скрытых шагов, нет знаний «в голове у аналитика».

### 2.2 Архитектура данных

Система реализует трёхслойную архитектуру DWH на базе DuckDB.

```

[Источники данных]
▼
┌─────────────────────────────────────────────────────┐
│ RAW-слой (сырые данные как есть)                    │
│ users · courses · enrollments · payments            │
│ payment_attempts · ad_costs                         │ └─────────────────────────────────────────────────────┘
init_db.py применяет фильтры
▼ 
┌─────────────────────────────────────────────────────┐
│ STAGING-слой (очищенные данные)                     │
│ stg_users · stg_courses · stg_enrollments           │
│ stg_payments · stg_payment_attempts · stg_ad_costs  │ └─────────────────────────────────────────────────────┘
metrics_mart.sql строит витрины
▼ 
┌─────────────────────────────────────────────────────┐
│ MARTS-слой (готовые метрики)                        │
│ mart_revenue · mart_conversion · mart_activity      │
│ mart_completion · mart_ad_performance               │ └─────────────────────────────────────────────────────┘
▼
[Потребители: дашборды · отчёты · SQL-запросы]

```

**RAW-слой** — зеркало источников. Данные загружаются без изменений. Этот слой никогда не изменяется вручную — только перезагружается из источников.

**Staging-слой** — очищенные данные. Здесь применяются фильтры из Data Dictionary: исключаются невалидные записи, дубли, технические аномалии. Все правила задокументированы в `staging_decisions.md`.

**Marts-слой** — готовые метрики. Каждая витрина закрывает потребности одного дашборда или отчёта. Потребители работают только с этим слоем — никакого самостоятельного SQL к сырым данным.

### 2.3 Источники данных в TO-BE системе

| Источник | Статус | Как интегрирован |
|---|---|---|
| Продакшн-база платформы | ✅ Реализован | CSV → raw-слой |
| Платёжная система (ЮКасса) | ✅ Частично | Данные включены в payments |
| Рекламные кабинеты (VK, Яндекс) | ✅ Реализован | CSV → raw.ad_costs |
| CRM (amoCRM) | ❌ Не реализован | Ежедневный ETL — в плане |
| Email-платформа (Unisender) | ❌ Не реализован | API-интеграция — в плане |

В продакшн-системе все источники подключаются через ETL-пайплайн, который запускается ежедневно по расписанию. В учебном проекте источники смоделированы синтетическими данными.

### 2.5 Система качества данных

Проверка качества встроена в процесс как обязательный шаг, а не как разовая операция.

**До очистки (raw):** `check_quality.py --source raw` выявляет все аномалии и сохраняет `reports/quality_raw.md`. Этот снимок фиксирует реальное состояние источников.

**После очистки (staging):** `check_quality.py --source staging` показывает, что осталось после применения фильтров. Сохраняется `reports/quality_staging.md`.

**Сравнение:** `check_quality.py --source compare` выводит таблицу изменений и итоговый процент устранённых аномалий.

**Результат в нашем проекте:**

| | До очистки | После очистки |
|---|---|---|
| Записей с ошибками | 737 | 5 |
| Снижение | | **−99%** |

Единственная оставшаяся аномалия — A4 (курсы с ценой 0). Она намеренно не фильтруется: решение о том, является ли нулевая цена ошибкой или бесплатным продуктом, должен принять продакт-менеджер, а не аналитик.

### 2.7 Что остаётся за рамками проекта

Следующие шаги выходят за рамки данного проекта и намечены как направления дальнейшего развития системы.
1. **Дашборд и система отчётности**. Подключение витрин к Tableau, визуализация всех пяти групп метрик, публикация на Tableau Public. Параллельно — разработка шаблонов для регулярных отчётов (финансовый, маркетинговый, когортный), обновляемых в один клик при пересчёте витрин. Цель: аналитик не тратит время на сборку отчётов вручную — только на интерпретацию.
2. **Миграция на ClickHouse.** DuckDB выбран для проекта как бесплатный аналог с совместимым SQL-диалектом, не требующий установки сервера. При росте данных до десятков миллионов строк и появлении нескольких одновременных пользователей рекомендуется миграция на колоночную СУБД — ClickHouse или Yandex DataLens. Архитектура трёх слоёв (raw → staging → marts) и SQL-скрипты витрин переносятся без переработки логики.
3. **Автоматизация ETL.** Настройка ежедневного запуска `init_db.py` по расписанию через cron или Airflow с автоматическими уведомлениями при сбое. Пока что пайплайн запускается вручную.
4. **Инкрементальная загрузка.** Сейчас база пересоздаётся полностью при каждом запуске. В продакшне при ежедневном приросте данных нужна инкрементальная загрузка: брать только новые записи за вчера, а не всю историю заново.
5. **Историчность данных (SCD2).** Если цена курса изменится, в текущей системе останется только актуальное значение — исторические отчёты пересчитать нельзя. В продакшне нужно хранить все версии изменяемых атрибутов с временными метками.
6. **Интеграция CRM и email-платформы.** Добавление данных о воронке продаж и рассылках разблокирует метрики, недоступные сейчас: конверсия из письма в покупку, эффективность менеджеров, причины отказа от покупки.
7. **Алерты при аномалиях.** Автоматическая отправка уведомления в Telegram или на email при обнаружении CRITICAL-аномалий в `check_quality.py`.
