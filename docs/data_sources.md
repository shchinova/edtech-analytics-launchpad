# Описание исходных данных

> Этот файл описывает синтетические данные проекта: что моделирует каждая таблица, какие поля содержит, по какой логике сгенерирована и какие ошибки заложены намеренно. Данные генерируются скриптом `generate_data.py`.

## 1. Общее

### Соответствие таблиц реальным источникам

В реальной онлайн-школе данные приходят из нескольких независимых систем. В проекте каждая система смоделирована отдельной таблицей или группой таблиц.

|Таблица|Реальный источник|Комментарий|
|---|---|---|
|`users`|Продакшн-база платформы|Регистрации и профили пользователей|
|`courses`|Продакшн-база платформы|Каталог продуктов|
|`enrollments`|Продакшн-база платформы|Записи на курсы, прогресс|
|`payments`|Продакшн-база + платёжный шлюз|Итоговые транзакции после webhook|
|`payment_attempts`|Платёжный шлюз (ЮКасса)|Все попытки, включая незавершённые|
|`ad_costs`|Рекламные кабинеты (VK, Яндекс)|Расходы, показы, клики по каналам|

Источники, которые в проекте не моделируются: CRM (amoCRM), email-платформа (Unisender). Причины — в разделе 4.

### Временной период

Все таблицы покрывают период **январь 2024 — июнь 2025** (18 месяцев). Единый период — обязательное условие согласованности: платёж не может быть раньше регистрации пользователя, реклама не может приводить пользователей раньше, чем она запущена.

### Сезонность

EdTech имеет выраженную сезонность. Она заложена в генератор и проявляется одинаково во всех таблицах — больше регистраций означает больше записей, больше платежей и больше расходов на рекламу в тот же период.

|Период|Характер|Коэффициент активности|
|---|---|---|
|Январь|Низкий сезон (праздники)|0.6|
|Февраль–март|Умеренный рост|0.9|
|Апрель–май|Пик (подготовка к ЕГЭ)|1.8|
|Июнь|Спад после ЕГЭ|0.7|
|Июль–август|Низкий сезон|0.5|
|Сентябрь|Второй пик (начало учебного года)|1.4|
|Октябрь–декабрь|Умеренная активность|1.0|

### Как запустить генерацию

```bash
pip install pandas numpy
python generate_data.py
```

Скрипт создаёт папку `data/raw/` и сохраняет в неё шесть CSV-файлов. Все параметры генерации задаются константами в начале скрипта.

## 2. Таблицы

### 2.1. `users` — пользователи платформы

**Что моделирует:** таблицу пользователей из продакшн-базы платформы. Каждая строка — один зарегистрированный пользователь.

**Количество строк:** 5 000

#### Поля

|Поле|Тип|Описание|
|---|---|---|
|`user_id`|integer|Уникальный идентификатор пользователя|
|`email`|string|Электронная почта (должна быть уникальной)|
|`age`|integer|Возраст на момент регистрации|
|`city`|string|Город пользователя|
|`channel`|string|Канал привлечения: organic, vk_ads, yandex_direct, telegram, referral, email|
|`registered_at`|datetime|Дата и время регистрации|
|`is_active`|integer|Флаг активности: 1 — активен, 0 — неактивен|

#### Бизнес-логика генерации

Возраст: 14–18 лет (школьники, целевая аудитория ЕГЭ) — 30%, 19–35 лет (взрослые) — 70%.

Распределение каналов привлечения:

|Канал|Доля|
|---|---|
|organic|35%|
|vk_ads|25%|
|yandex_direct|18%|
|telegram|10%|
|referral|7%|
|email|5%|

География: Москва — 28%, Санкт-Петербург — 15%, другие крупные города — по 4–7%, прочие — 16%.

Регистрации подчиняются сезонности: пик в апреле–мае и сентябре.

#### Намеренные ошибки

|Ошибка|Количество|Зачем заложена|
|---|---|---|
|Дублирующиеся email|~50 записей|Моделирует ситуацию, когда пользователь зарегистрировался дважды с одной почтой. Нельзя уникально идентифицировать пользователя — напрямую искажает метрики уникальных пользователей|
|Дата регистрации в будущем|~30 записей|Типичная ошибка серверного времени или тестовые аккаунты. Такие пользователи не должны попадать в когортный анализ до наступления даты|

### 2.2. `courses` — каталог курсов

**Что моделирует:** таблицу продуктового каталога из продакшн-базы. Каждая строка — один курс или подписка.

**Количество строк:** 120

#### Поля

|Поле|Тип|Описание|
|---|---|---|
|`course_id`|integer|Уникальный идентификатор курса|
|`title`|string|Название курса|
|`subject`|string|Предмет: Математика, Русский язык, Физика, Химия, Биология, История, Обществознание, Английский язык, Информатика|
|`level`|string|Уровень: Базовый, Продвинутый, Эксперт|
|`course_type`|string|Тип продукта: Курс, Интенсив, Подписка|
|`price_rub`|integer|Цена в рублях (0 для бесплатных)|
|`duration_weeks`|integer|Длительность в неделях (NULL для подписок)|
|`created_at`|datetime|Дата создания курса в системе|
|`is_published`|integer|Флаг публикации: 1 — опубликован, 0 — черновик|

#### Бизнес-логика генерации

Распределение предметов: математика и русский язык — по 20% (основные предметы ЕГЭ), физика/химия/биология/обществознание — по 10%, остальные — по ~7%.

Типы и базовые цены:

|Тип|Доля|Базовая цена|
|---|---|---|
|Курс|55%|2 900 — 9 900 ₽ в зависимости от уровня|
|Интенсив|25%|+30% к цене курса того же уровня|
|Подписка|20%|990 — 2 900 ₽/мес|

Длительность: интенсив 4–8 недель, базовый курс 8–12 недель, продвинутый 12–16 недель, эксперт 16–24 недели. Для подписок `duration_weeks` = NULL.

#### Намеренные ошибки

| Ошибка          | Количество | Зачем заложена                                                                                                                                 |
| --------------- | ---------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Курсы с ценой 0 | 5 курсов   | Моделирует ошибку заведения продукта — курс создан без цены. Если не фильтровать, такие курсы попадают в расчёт выручки и искажают средний чек |

### 2.3. `enrollments` — записи на курсы

**Что моделирует:** таблицу записей пользователей на курсы из продакшн-базы. Каждая строка — одна запись конкретного пользователя на конкретный курс.

**Количество строк:** ~17 000

#### Поля

|Поле|Тип|Описание|
|---|---|---|
|`enrollment_id`|integer|Уникальный идентификатор записи|
|`user_id`|integer|Ссылка на `users.user_id`|
|`course_id`|integer|Ссылка на `courses.course_id`|
|`enrolled_at`|datetime|Дата и время записи на курс|
|`status`|string|Статус: active, completed, dropped, paused|
|`progress_pct`|integer|Прогресс прохождения, 0–100|

#### Бизнес-логика генерации

Задержка от регистрации до записи: 0–1 день — 40%, 2–7 дней — 35%, 8–30 дней — 20%, более 30 дней — 5%.

Распределение статусов:

|Статус|Доля|Логика прогресса|
|---|---|---|
|completed|28%|progress = 100%|
|active|35%|progress от 1% до 99%|
|dropped|25%|progress от 5% до 60%|
|paused|12%|progress от 20% до 75%|

Количество курсов на пользователя: 1 курс — 50%, 2–3 курса — 35%, 4+ — 15%.

Популярность курсов коррелирует с распределением предметов: математика и русский язык получают в 2–3 раза больше записей, чем редкие предметы.

#### Намеренные ошибки

|Ошибка|Количество|Зачем заложена|
|---|---|---|
|`enrolled_at` раньше `registered_at` пользователя|~100 записей|Физически невозможная ситуация — моделирует ошибку ETL или проблему с часовыми поясами. Такие записи должны быть найдены проверкой качества и исключены из воронки|

### 2.4. `payments` — транзакции

**Что моделирует:** итоговую таблицу платежей, которая в реальной системе формируется из двух источников: платёжный шлюз подтверждает транзакцию, продакшн-база записывает факт оплаты и привязывает к записи пользователя. В проекте эти два источника объединены в одну таблицу.

**Количество строк:** ~11 000

#### Поля

|Поле|Тип|Описание|
|---|---|---|
|`payment_id`|integer|Уникальный идентификатор платежа|
|`user_id`|integer|Ссылка на `users.user_id`|
|`course_id`|integer|Ссылка на `courses.course_id`|
|`enrollment_id`|integer|Ссылка на `enrollments.enrollment_id`|
|`paid_at`|datetime|Дата и время платежа|
|`amount_rub`|integer|Итоговая сумма платежа с учётом скидки|
|`base_price`|integer|Базовая цена курса на момент оплаты|
|`discount_pct`|integer|Скидка в процентах (0 если не применялась)|
|`status`|string|Статус: success, refunded, failed|
|`payment_method`|string|Метод оплаты: card, sbp, wallet|

#### Бизнес-логика генерации

Платёж генерируется только для записей на платные курсы (price_rub > 0). Конверсия enrollment → payment: 65% записей на платные курсы имеют оплату.

Скидки применяются к 20% платежей: 10%, 15%, 20% или 30%. Скидки чаще встречаются в низкий сезон (январь, июль–август).

Методы оплаты: карта — 65%, СБП — 25%, кошелёк — 10%.

Возвраты: 8% платежей получают статус `refunded`. Возвраты чаще встречаются на дорогих курсах и в первые 7 дней после оплаты.

Подписки генерируют повторные платежи каждые 30 дней, пока статус enrollment активен.

#### Намеренные ошибки

|Ошибка|Количество|Зачем заложена|
|---|---|---|
|Отрицательная сумма (`amount_rub < 0`)|40 записей|Моделирует ситуацию, когда возвраты закодированы как отрицательные платежи вместо отдельного типа транзакции. Включение в выручку занижает показатели|
|Нулевая сумма при статусе success|20 записей|Ошибка интеграции со шлюзом — платёж прошёл, но сумма не записалась. Если не фильтровать, занижает средний чек|

### 2.5. `payment_attempts` — попытки оплаты

**Что моделирует:** данные платёжного шлюза о всех попытках транзакции, включая незавершённые. В реальной системе эти данные недоступны из продакшн-базы — они хранятся только в личном кабинете шлюза.

**Количество строк:** ~15 000

#### Поля

|Поле|Тип|Описание|
|---|---|---|
|`attempt_id`|integer|Уникальный идентификатор попытки|
|`user_id`|integer|Ссылка на `users.user_id` (может быть NULL при orphan records)|
|`course_id`|integer|Ссылка на `courses.course_id`|
|`attempted_at`|datetime|Дата и время попытки|
|`result`|string|Результат: success, failed, abandoned|
|`failure_reason`|string|Причина неудачи: insufficient_funds, card_declined, timeout, user_cancelled, NULL для success|
|`payment_method`|string|Метод оплаты: card, sbp, wallet|

#### Бизнес-логика генерации

Каждый успешный платёж из `payments` имеет ровно одну соответствующую попытку со статусом `success`. Это жёсткое правило — без него воронка оплаты не сойдётся.

Дополнительно генерируются незавершённые попытки. На каждые 100 успешных: ~40 failed и ~25 abandoned.

Распределение причин неудачи:

|Причина|Доля|
|---|---|
|user_cancelled|40%|
|insufficient_funds|25%|
|card_declined|20%|
|timeout|15%|

Хронологическое правило: если у пользователя несколько попыток на один курс, они идут в порядке времени — сначала failed/abandoned, последняя — success.

#### Намеренные ошибки

|Ошибка|Количество|Зачем заложена|
|---|---|---|
|Orphan records — попытки без соответствующего `user_id` в `users`|~200 записей|Моделирует ситуацию, когда пользователь начал оплату без завершения регистрации (гостевой чекаут) или данные были удалены. Такие записи не должны ломать расчёты воронки|

### 2.6. `ad_costs` — расходы на рекламу

**Что моделирует:** ежедневные выгрузки из рекламных кабинетов ВКонтакте и Яндекс.Директ. В реальной системе эти данные не связаны с продакшн-базой — аналитик получает их отдельно через API или ручную выгрузку.

**Количество строк:** ~500 (по одной строке на канал в день для платных каналов)

#### Поля

|Поле|Тип|Описание|
|---|---|---|
|`date`|date|Дата (агрегация по дням)|
|`channel`|string|Канал: vk_ads, yandex_direct, telegram|
|`impressions`|integer|Количество показов|
|`clicks`|integer|Количество кликов|
|`spend_rub`|integer|Расходы в рублях|

#### Бизнес-логика генерации

Только платные каналы: vk_ads, yandex_direct, telegram. Organic и referral рекламных расходов не имеют.

Средние дневные бюджеты:

|Канал|Дневной бюджет|Примечание|
|---|---|---|
|vk_ads|15 000 — 45 000 ₽|Основной канал|
|yandex_direct|10 000 — 35 000 ₽|Второй по объёму|
|telegram|3 000 — 10 000 ₽|Небольшой, но качественный|

В апреле–мае бюджеты увеличиваются в 2–2.5 раза — школа агрессивно набирает студентов перед ЕГЭ. В июле–августе бюджеты минимальные.

CTR (клики / показы): VK — 0.8–1.5%, Яндекс — 2–4%, Telegram — 3–6%.

Количество новых пользователей из платного канала коррелирует с расходами на этот канал в тот же период — это позволяет считать реалистичный CAC.

#### Намеренные ошибки

|Ошибка|Количество|Зачем заложена|
|---|---|---|
|Нулевые расходы при ненулевых показах|~15 строк|Моделирует ошибку выгрузки из рекламного кабинета — данные о показах пришли, данные о расходах потерялись. Такие строки искажают CPM и должны быть отфильтрованы|
|Даты в будущем|несколько строк|Ошибка при ручной выгрузке или тестовая запись в кабинете|

## 3. Согласованность между таблицами

Генератор соблюдает следующие правила связности. Нарушение каждого из них — отдельный тип аномалии, который выявляется скриптом `check_quality.py`.

|#|Правило|Таблицы|
|---|---|---|
|1|Каждый `enrollment.user_id` существует в `users`|enrollments → users|
|2|Каждый `enrollment.course_id` существует в `courses`|enrollments → courses|
|3|`enrolled_at` >= `registered_at` пользователя (кроме ~100 намеренных ошибок)|enrollments + users|
|4|Каждый `payment.user_id` существует в `users`|payments → users|
|5|Каждый `payment.course_id` существует в `courses`|payments → courses|
|6|Каждый `payment.enrollment_id` существует в `enrollments`|payments → enrollments|
|7|`paid_at` >= `enrolled_at` соответствующего enrollment|payments + enrollments|
|8|Платёж существует только на курс с `price_rub > 0`|payments + courses|
|9|Каждый `payment_attempt` со статусом `success` имеет ровно один соответствующий `payment`|payment_attempts + payments|
|10|`ad_costs` содержит только каналы vk_ads, yandex_direct, telegram|ad_costs|
|11|Сезонность регистраций коррелирует с сезонностью расходов на рекламу|users + ad_costs|

## 4. Ограничения датасета

### Что не смоделировано и почему

**CRM (amoCRM).** Реалистичная генерация CRM-данных потребовала бы моделирования воронки продаж, звонков, задач менеджеров и статусов сделок. Это значительный объём работы при невысокой аналитической ценности для данного проекта: ключевые метрики считаются без CRM-данных. В реальной системе CRM подключается через ежедневный ETL. Метрики, недоступные без CRM: детальная воронка продаж по менеджерам, причины отказа от покупки, LTV в разрезе источника лида.

**Email-платформа (Unisender).** По аналогичной причине: данные об открытиях и кликах писем требуют отдельной генерации кампаний, сегментов и поведенческих событий. Метрики, недоступные без этих данных: open rate, click rate, конверсия из письма в покупку.

**Сессионные данные (события на сайте).** В реальной системе есть таблица events или sessions — каждый просмотр страницы, клик, время на сайте. В проекте активность пользователя моделируется косвенно через `enrollments` и `progress_pct`. DAU/WAU/MAU считаются как прокси-метрики на основе дат записей, а не реальных сессий.

### Что это означает для метрик

|Метрика|Доступна?|Причина ограничения|
|---|---|---|
|CAC (стоимость привлечения)|✅ Частично|Считается по платным каналам, organic не учитывается|
|ROAS|✅ Частично|Только для платных каналов|
|Воронка продаж по менеджерам|❌|Нет CRM|
|Конверсия из email-рассылки|❌|Нет данных email-платформы|
|DAU/WAU (реальные)|⚠️ Прокси|Считается через enrollments, не через сессии|
|Retention (реальный)|⚠️ Прокси|Считается через повторные записи, не через заходы|
