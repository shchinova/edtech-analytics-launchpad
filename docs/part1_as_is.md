# Часть 1. AS-IS: как устроена аналитика до трансформации

## 1. Компания

**ЕГЭ Экспресс** — онлайн-школа по подготовке к ЕГЭ и ОГЭ. Основные продукты: курсы по предметам (математика, русский язык, физика и др.), интенсивы перед экзаменами и помесячные подписки с доступом к материалам. Аудитория — школьники 14–18 лет и их родители, а также взрослые, которые проходят курсы для повышения квалификации.

Компания работает три года, база — около 5 000 зарегистрированных пользователей, 120 активных курсов. Выручка растёт, но вместе с ней растёт и количество вопросов, на которые аналитика не может дать быстрый и надёжный ответ.

## 2. Источники данных

### 2.1. Продакшн-база платформы (основной источник)

Каждое действие пользователя на сайте: регистрация, запись на курс, прогресс по урокам — автоматически записывается в реляционную базу данных (PostgreSQL). Здесь хранится всё, что связано с поведением пользователя на платформе: таблицы пользователей, курсов, записей, прогресса.

Аналитик работает с репликой базы — копией, которая обновляется каждые несколько часов. Это стандартная практика: прямая работа с продакшн-базой замедляет сайт и создаёт риск случайного изменения данных.

### 2.2. Платёжная система

Оплата проходит через внешний шлюз (ЮКасса). После успешной транзакции шлюз отправляет уведомление (webhook) на сервер платформы, и платёж записывается в продакшн-базу. Данные о платежах доступны аналитику через реплику базы, но детали попыток оплаты (незавершённые транзакции, отказы банка) остаются только в личном кабинете шлюза.

### 2.3. Рекламные кабинеты

Платное привлечение идёт через ВКонтакте и Яндекс.Директ. Данные о расходах, показах и кликах хранятся в рекламных кабинетах и в продакшн-базу не попадают. Канал привлечения пользователя фиксируется в базе при регистрации (UTM-метки), но стоимость привлечения — нет.

### 2.4. CRM

Отдел продаж работает в amoCRM: фиксирует заявки, звонки, статусы сделок. Данные из CRM в продакшн-базу не передаются — это изолированная система. Для сводного анализа менеджер раз в неделю выгружает отчёт вручную в Excel.

### 2.5. Email-платформа

Рассылки отправляются через Unisender. Данные об открытиях и кликах хранятся только внутри платформы, в аналитику не передаются.

> **В проекте** каждый из этих источников смоделирован отдельным CSV-файлом. Подробное описание таблиц, полей и намеренно заложенных ошибок — в `data_sources.md`.

## 3. Как сейчас работает аналитика

### Инструменты

Единственный инструмент — SQL-запросы к реплике продакшн-базы. Витрин данных нет. Каждый аналитический вопрос решается новым запросом, написанным с нуля. Запросы хранятся в shared-папке без версионирования, часть существует только в головах у людей.

### Кто считает метрики

Метрики считают три человека: аналитик, продакт-менеджер и руководитель маркетинга. У каждого своя версия SQL-запроса для одних и тех же показателей. Определения нигде не зафиксированы, поэтому цифры регулярно расходятся.

Типичная ситуация: на еженедельном совещании аналитик называет конверсию 4,2%, маркетолог — 6,1%. Полчаса уходит на выяснение, кто считал от зарегистрированных, а кто от записавшихся. Решение не документируется, на следующей неделе история повторяется.

### Как попадают данные из разных источников

Данные из рекламных кабинетов и CRM в базу не интегрированы. Процесс ручной:
- Маркетолог раз в неделю скачивает отчёт из кабинета ВКонтакте в Excel и отправляет аналитику.
- Аналитик вручную скачивает платежи из личного кабинета ЮКассы в CSV и сверяет с базой.
- Данные из CRM запрашиваются у руководителя продаж отдельно, по необходимости.

Сводная картина «регистрации + расходы на рекламу + выручка» существует только в голове аналитика и пересобирается каждый раз вручную.

### Отчётность

Регулярной автоматической отчётности нет. Есть дашборд для руководства в Google Таблицах, который аналитик обновляет вручную раз в неделю. Если аналитик заболел или ушёл в отпуск — дашборд не обновляется.

## 4. Проблемы текущей системы

Все проблемы можно свести к одному корню: **аналитика держится на одном человеке и ручных процессах**. Это создаёт четыре класса рисков.

- **Ненадёжность цифр.** Метрики считаются по-разному в разных отделах, определения нигде не зафиксированы. Бизнес-решения принимаются на основе цифр, в корректности которых нельзя быть уверенным.

- **Непрозрачность данных.** Часть логики расчётов существует только в SQL-запросах без комментариев и только на компьютере аналитика. Если человек уходит — знание уходит вместе с ним.

- **Слепые зоны.** Метрики привлечения (CAC, ROAS) посчитать нельзя, потому что расходы на рекламу не интегрированы с данными платформы. Воронка обрывается на шаге «пришёл на сайт» — что было до этого, неизвестно.

- **Хрупкость процессов.** Любой ручной шаг — потенциальная точка отказа. Маркетолог забыл прислать выгрузку — нет данных по каналам. Аналитик заболел — нет дашборда. Система не работает сама по себе.

## 5. Что нужно изменить

Из анализа текущего состояния вытекают задачи, которые решает этот проект:
1. Зафиксировать определения всех ключевых метрик в едином Data Dictionary.
2. Интегрировать все источники данных в одно хранилище.
3. Построить слой витрин данных — чтобы метрики считались одинаково для всех.
4. Автоматизировать проверку качества данных.
5. Снизить зависимость от одного человека через документацию и воспроизводимые скрипты.
